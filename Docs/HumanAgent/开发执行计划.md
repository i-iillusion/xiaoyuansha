## 1. 固定工作法：任何模型都不得跳过

### 1.1 开始一项任务

1. `git status`、分支/远端核对，识别工作区文件归属。只做安全的快进或清楚范围的合并，遇同文件冲突先读双方含义，不整文件选ours/theirs。
2. 认领最前面的可执行`DEV-*`子任务；列源规则ID、受影响入口、预期行为和明确不做的部分。
3. 阅读对应原文与最新裁决，查看整段生产调用链、测试调用链和异步返回点。不能只改一个同名helper。
4. 若同一局面可能产生两种结果，先登记问题并问用户；所有问题保留“不清楚”。只暂停依赖该答案的分支，其他明确工作继续。

### 1.2 修改与验证

1. 先增加反例/回归数据，再修最小公共入口和所有相关调用者；不通过改预期来迁就当前代码。
2. 单个测试先明确“通常任意牌”，再加“已具体牌原实例”变体；每种路径至少覆盖成功、拒绝/取消、状态过期和下一次合法操作。
3. 明确验证层级：纯逻辑、真实GameManager入口、UI输入恢复；只有helper验证的条目不能写“完整技能已验收”。
4. 保留项目约定：未经用户明确要求不手动运行游戏测试。允许`git diff --check`、只读引用/调用/链接检查；运行行为交由现有推送CI。需要额外手工试玩时单独说明目的并请用户安排。
5. 当前自动CI固定七组：test_rule_settlement、test_confirmed_rules、test_bill、test_hand_payment、test_card_transfer、test_identity_victory、test_free_for_all_victory。新case必须由其中相应入口调用；仅创建脚本不算接入。
6. CI须导入成功、各组正常退出、RESULT零失败、无SCRIPT ERROR/ERROR/Parse Error/FAIL且未超时。保留日志和SHA对应关系，不引用上一批绿灯代替本批。

### 1.3 提交关卡

- 单个子任务通常单独提交；同一问题的代码和回归一起，文档与行为变更尽量分开。不可为了凑数量宣布大里程碑完成。
- 只暂存本批明确文件，审阅cached diff，不用无差别`git add .`纳入用户PDF或上轮草稿。
- 推送dev，等待自动CI；失败先修该批、另提交，不降低门槛、不静默删案例。没有新授权不合main、不强推。
- 更新本页交付账本、QA与当前交接：任务、SHA、CI链接、状态、未覆盖项、精确下一步。不要同时保留多段相互冲突的“当前”。
